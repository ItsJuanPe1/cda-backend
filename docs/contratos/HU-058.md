# Contrato API: HU-058 Consultar una bitácora de cambios

**Estado:** aprobado (2026-11-06), implementado en backend · **Fecha:** 2026-11-06
**HU relacionadas:** HU-047 (consumidor del servicio), HU-001/006/010 (login), HU-055 y RN-15 (ventanas de fechas)
**Migración:** V29 (`V29__hu058_create_bitacora.sql`), probada en PostgreSQL 17.11 local

## Alcance
1. Un servicio interno `BitacoraService` que cualquier servicio llama **dentro de su misma transacción** para dejar
   rastro de un cambio. Si el registro falla, la operación completa falla (rollback).
2. El registro de ingresos aceptados y rechazados desde `GoogleAuthService`.
3. Un endpoint de **solo lectura** para el administrador, con filtros y paginación.

No hay endpoints para crear, modificar ni borrar registros. La base de datos también lo impide con un trigger (C4).

## Roles
| Endpoint | Roles |
|---|---|
| `GET /api/bitacora` | `ADMIN` |

Cualquier otro método (`POST`, `PUT`, `PATCH`, `DELETE`) sobre `/api/bitacora` y `/api/bitacora/**` responde
**405** para el administrador y **403** para los demás roles.

## Modelo
Tabla `bitacora`:

| Campo | Tipo | Notas |
|---|---|---|
| `id` | bigint | Llave primaria. |
| `fecha` | timestamptz | En UTC, la asigna el servidor. |
| `usuario_correo` | texto o `null` | Correo institucional de la cuenta autenticada. Es `null` en ingresos rechazados sin correo institucional verificado. |
| `usuario_rol` | `ADMIN` \| `COORDINADOR` \| `DOCENTE` o `null` | Rol con el que operó. |
| `operador_nombre` | texto o `null` | Solo para rol `COORDINADOR`: `nombreCompleto` del coordinador de la sesión (el asignado al programa en ese momento). Se copia al registrar, así un cambio posterior de coordinador no altera el histórico. `null` para otros roles. |
| `accion` | texto | `CREAR`, `EDITAR`, `DESACTIVAR`, `REACTIVAR`, `ELIMINAR`, `INGRESO`. |
| `entidad` | texto | Ej. `PERIODO`, `PROGRAMA`, `CURSO`, `SESION`. |
| `entidad_id` | texto o `null` | Identificador de la entidad (texto, porque hay llaves como `code_course`). |
| `periodo_id` | bigint o `null` | FK a `periodos_academicos` (`ON DELETE RESTRICT`). Lo envía el servicio que llama cuando la entidad pertenece a un periodo académico. En ingresos queda `null`. |
| `valor_anterior` | jsonb o `null` | Estado antes del cambio. |
| `valor_nuevo` | jsonb o `null` | Estado después del cambio. |
| `resultado` | `ACEPTADO` \| `RECHAZADO` o `null` | Solo para `accion = INGRESO` (obligatorio en ese caso). |
| `motivo` | texto o `null` | Motivo del rechazo (ver tabla). |

### Motivos de rechazo de ingreso
| `motivo` | Cuándo |
|---|---|
| `TOKEN_INVALIDO` | El token de Google no es válido, está vencido o falta. |
| `DOMINIO_NO_INSTITUCIONAL` | Correo no verificado o fuera de `@correounivalle.edu.co`. No se guarda el correo. |
| `CUENTA_NO_REGISTRADA` | El correo no existe en ningún perfil. |
| `SIN_PERFIL_ROL` | Existe, pero no tiene el rol solicitado. |
| `PERFIL_DESACTIVADO` | El perfil está desactivado. |
| `FUERA_DE_VENTANA` | Fuera de las fechas de RN-15. Queda definido pero **sin uso** en esta HU: se empieza a registrar cuando se implemente la validación de ventanas (RN-15/HU-055). |

### Datos que no se guardan (Ley 1581)
- Nunca se guarda el token de Google ni el JWT emitido.
- Si el ingreso se rechaza por dominio, no se guarda el correo (puede ser personal).
- En `valor_anterior` y `valor_nuevo`, el servicio que llama envía solo los campos de negocio que cambian. No se
  guardan fotos ni campos binarios.

## Servicio interno (no es endpoint)

```java
// Dentro de la transacción del llamador (Propagation.MANDATORY): si no hay transacción, falla.
bitacoraService.registrar(accion, entidad, entidadId, periodoId, valorAnterior, valorNuevo);

// Para ingresos: transacción propia (REQUIRES_NEW), para que el rechazo quede registrado
// aunque el login termine en excepción.
bitacoraService.registrarIngreso(correo, rol, resultado, motivo);
```

El usuario y el rol se toman del `SecurityContext` (JWT). Si un ingreso aceptado no se puede registrar, el login
falla (no se emite sesión sin rastro).

## GET /api/bitacora

### Parámetros de consulta (todos opcionales)
| Parámetro | Tipo | Regla |
|---|---|---|
| `usuario` | texto | Coincidencia parcial, sin distinguir mayúsculas, sobre `usuario_correo` (y `operador_nombre` si se aprueba). |
| `entidad` | texto | Coincidencia exacta, sin distinguir mayúsculas. |
| `periodoId` | entero | Id de `periodos_academicos`. |
| `desde` | fecha `YYYY-MM-DD` | Inclusivo, desde las 00:00 de ese día en `America/Bogota`. |
| `hasta` | fecha `YYYY-MM-DD` | Inclusivo, hasta las 23:59:59 de ese día en `America/Bogota`. |
| `pagina` | entero ≥ 0 | Por defecto `0`. |
| `tamano` | entero de 1 a 100 | Por defecto `20`. |

Orden fijo: `fecha` descendente y luego `id` descendente.

### Errores
| Código | Cuándo | Mensaje |
|---|---|---|
| 400 | `desde` posterior a `hasta` | «La fecha inicial no puede ser posterior a la fecha final» (supuesto, la HU no define mensaje) |
| 400 | Fecha con formato inválido, `pagina` < 0, `tamano` fuera de 1 a 100 | «Parámetros de consulta inválidos» (supuesto) |
| 401 | Sin token | (manejo estándar de Spring Security) |
| 403 | Rol distinto de `ADMIN` | (manejo estándar de Spring Security) |
| 405 | `POST`/`PUT`/`PATCH`/`DELETE` | Método no permitido (C4) |

## Decisiones de las dudas (2026-11-06)
1. **Persona que operó la cuenta compartida:** opción (a), el `nombreCompleto` del coordinador asignado al programa.
2. **Fuera de fechas:** se deja el motivo `FUERA_DE_VENTANA` listo; la validación de ventanas se hace con RN-15/HU-055.
3. **Filtro «periodo»:** es el periodo académico (`periodos_academicos`).
