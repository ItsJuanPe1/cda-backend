# Contrato API: HU-049 Asociar docentes a las asignaturas que han dictado

**Estado:** implementado, pendiente de aprobación · **Fecha:** 2026-11-03 · **Actualizado:** 2026-11-12
**HU relacionadas:** HU-026 (docentes), HU-040 (programas), HU-017/HU-032 (mallas), HU-045 (programación)
**Migraciones:** V27 (tabla inicial) y V28 (`V28__docente_asignatura_por_facultad.sql`)

## Alcance
El administrador mantiene el histórico de asignaturas que cada docente ha dictado. Puede asociar y quitar
asignaturas y consultar por docente, asignatura, facultad o estado. La asociación queda ligada a la **facultad de
adscripción del docente**; el administrador no elige programa ni facultad. Cuando un docente queda asignado a un
curso de un periodo, la asociación se agrega automáticamente. No hay borrado físico: quitar una asociación la
desactiva (RN-13).

No existe carga inicial por CSV. Es un módulo **nuevo**; no cambia endpoints existentes. `ProgramacionService` se
integra con el histórico al generar la programación.

## Roles
| Endpoint | Roles |
|---|---|
| `GET /api/docentes-asignaturas` | `ADMIN` |
| `POST /api/docentes-asignaturas` | `ADMIN` |
| `PATCH /api/docentes-asignaturas/{id}/estado` | `ADMIN` |
| `DELETE /api/docentes-asignaturas/{id}` | `ADMIN` |

`SecurityConfig` deja estos endpoints en la regla general de `/api/**` para administrador.

## Modelo
Tabla `docente_asignatura`:

| Campo | Tipo | Notas |
|---|---|---|
| `id` | bigint | Llave primaria. |
| `docente_id` | bigint | FK a `docentes`. |
| `code_course` | texto | FK a `asignaturas`. |
| `id_facultad` | entero | FK a `"Facultad"`. Se deriva del docente. |
| `periodo_id` | bigint o `null` | Periodo en el que se dictó, cuando viene de programación. |
| `origen` | `MANUAL` \| `PROGRAMACION` | Cómo se creó la asociación. |
| `activo` | booleano | Una asociación inactiva sigue en el histórico. |
| `created_at`, `updated_at` | timestamp | |
| `desactivado_at` | timestamp o `null` | Se llena al quitar la asociación. |

Llave única: `(docente_id, code_course, id_facultad)`.

La facultad se resuelve así: primero `docente.facultad`; si no está, la facultad del programa de adscripción del
docente. Si no se puede resolver, la asociación se rechaza con 400.

## Regla de perfil (criterio 3)
Una asignatura corresponde al perfil del docente si se cumple **cualquiera** de estas condiciones:

1. La asignatura tiene `id_facultad` igual a la facultad del docente.
2. La asignatura está en la malla registrada de algún programa de la facultad del docente
   (`pensum_academico`, cualquier versión).

Si el docente no tiene facultad ni programa, no se puede validar el perfil y se rechaza con 400.

## 1. `GET /api/docentes-asignaturas`: consultar

### Parámetros (query, opcionales)
| Parámetro | Tipo | Notas |
|---|---|---|
| `docenteId` | entero | Filtra por docente. |
| `codeCourse` | texto | Filtra por asignatura; se normaliza a mayúsculas. |
| `idFacultad` | entero | Filtra por facultad. |
| `activo` | `true` \| `false` | Si se omite, devuelve activas e inactivas. |

Los filtros se combinan con Y. Orden: apellidos y nombres del docente, luego nombre de la asignatura.

**200 OK**: arreglo de asociaciones. Arreglo vacío si no hay resultados.

## 2. `POST /api/docentes-asignaturas`: asociar individualmente

**Petición**
```json
{
  "docente_id": 7,
  "code_course": "MAT101"
}
```

**201 Created**: la asociación creada, con `origen = "MANUAL"` y `activo = true`.
Si ya existía una asociación inactiva para el mismo docente, asignatura y facultad, se reactiva y se responde
**201** con `origen = "MANUAL"`.

Para asociar varias asignaturas, el frontend repite la petición por cada una. Así puede informar cuáles fallaron sin
perder las que sí se guardaron.

## 3. `DELETE /api/docentes-asignaturas/{id}`: quitar

Desactiva la asociación (`activo = false`, `desactivado_at` con la fecha). No borra la fila (RN-13).

**204 No Content**. **404** si no existe.

## 4. `PATCH /api/docentes-asignaturas/{id}/estado?activo=true|false`: activar o desactivar

**200 OK**: la asociación actualizada. Al reactivar se limpia `desactivado_at`.

## Criterio 4: registro automático desde programación

Al generar o regenerar la programación, `ProgramacionService` llama a `registrarDesdeCursos` con los cursos que tienen
docente. Para cada curso se crea la asociación con `origen = "PROGRAMACION"` o se reactiva si ya existía, y se guarda el periodo del curso. La
facultad se deriva del programa del curso y, si falta, de la asignatura.

Como respaldo, la migración V28 reemplaza el trigger `trg_curso_docente_historico` en `cursos_programacion`
(`AFTER INSERT OR UPDATE OF id_docente`). El trigger hace el mismo `INSERT ... ON CONFLICT` y evita duplicados por la
llave única. V27 hace el backfill inicial y V28 migra esas filas a facultad.

## Sincronización del histórico visible (corrección 2026-11-12)

La pantalla de asociaciones también debe mostrar las asignaturas que un docente ya dictó y que todavía no tienen una
fila en `docente_asignatura`. Para completarlas, el backend sincroniza desde dos fuentes:

1. `cursos_programacion`: cursos con docente asignado y estado distinto de `EXCLUIDO`.
2. `evaluaciones_docentes`: calificaciones registradas. Es una fuente **complementaria**, porque solo contiene las
   asignaturas con nota registrada, no todo el histórico.

Para cada combinación `(docente, asignatura, facultad)`:

- Si no existe en `docente_asignatura`, se crea activa, con `origen = "PROGRAMACION"` y el periodo más reciente de
  las fuentes.
- Si ya existe, **no se modifica**: se conserva su origen, su periodo y su estado. Una asociación manual inactiva
  sigue inactiva.
- La facultad se resuelve desde el programa del curso, luego desde la asignatura y, para evaluaciones sin curso,
  desde la facultad del docente.
- No se crean duplicados por la llave única `(docente_id, code_course, id_facultad)`.

La sincronización se ejecuta de forma idempotente al iniciar la aplicación y, después de guardar una evaluación, para
el curso evaluado. Se hace en una transacción independiente: si falla, no bloquea el guardado de la calificación.

No agrega endpoints ni campos al contrato. No requiere migración nueva; la V34 queda reservada para HU-050.

## Validaciones y errores

| Código | Cuándo | Mensaje |
|---|---|---|
| 400 | Docente inactivo | «El docente está inactivo» |
| 400 | Asignatura inactiva | «La asignatura está inactiva» |
| 400 | La asignatura no pertenece a la facultad | «La asignatura no corresponde a la facultad de adscripción del docente» |
| 400 | Docente sin facultad ni programa | «El docente no tiene facultad de adscripción para validar su perfil» |
| 404 | Docente, asignatura o asociación inexistente | Mensaje específico |
| 409 | Asociación activa duplicada | «Ya existe la asociación del docente con la asignatura en su facultad» |
| 401/403 | Sin token o rol distinto de `ADMIN` | Respuesta de Spring Security |

## Fuera de este contrato
- Carga inicial por CSV o Excel.
- Edición del periodo de una asociación existente; se quita y se vuelve a crear.
- Historial de cambios de la asociación (HU-058, sin sprint).
